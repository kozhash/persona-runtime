# persona-runtime

**Telegram-персонаж с искусственной психикой.** Не ассистент и не
чат-бот с промптом: у него есть эпизодическая память с забыванием,
аффективная модель (PAD + appraisal), социальная боль, руминация,
циркадный сон и консолидация памяти во сне.

Персонаж живёт в Telegram через нативный **tdlib** (не Bot API):
печатает с задержкой, дробит сообщения, может молчать, ставить
реакции, писать первой — как человек, а не как сервис.

> **Статус: активная разработка (v0.1.x).** Архитектура стабильна,
> API и схема БД ещё могут меняться. Часть вещей сознательно
> недоделана — см. раздел «Известные ограничения».

---

## Зачем это

Большинство «персонажей» на LLM — это системный промпт плюс история
чата. Характер в них держится на тексте промпта и разваливается на
длинной дистанции: персонаж «забывает», что ему говорили, отвечает
одинаково на грубость и на нежность, не устаёт, не спит и не меняется.

Здесь характер вынесен из промпта в **состояние**:

- что случилось — записывается в память с эмоциональной окраской;
- память затухает, консолидируется и переигрывается во сне;
- состояние (valence / arousal / dominance, усталость, социальная
  боль) **меняет то, как персонаж говорит**, а не только то, что
  он говорит;
- недоплаченное внимание и обида накапливаются и влияют на
  следующие ответы, а не исчезают с новым сообщением.

Промпт описывает, *кто* это. Состояние определяет, *как* он сейчас
себя ведёт.

## Система памяти

Память — не список сообщений, а многослойная структура
(`kuni/memory/`).

### Слои

| Слой | Модуль | Что делает |
|---|---|---|
| Эпизодическая память | `memory/episodic.py` | Эпизоды с эмбеддингами, актор-подобной ценностью (ACT-R), PAD-координатами и провенансом |
| Ассоциативный граф (CA3) | `memory/episodic.py` | Гиббсовские рёбра между эпизодами, вес затухает, связи усиливаются при совместной активации |
| Семантика (неокортекс) | `memory/episodic.py`, `memory/schema.py` | Пропозиции и битемпоральные факты: «что было правдой когда» |
| Рабочая память | `memory/working.py` | Короткий буфер текущего разговора |
| Дневник | `memory/diary.py` | Фасад записи: эмоциональные заметки от первого лица |
| Извлечение | `memory/retrieval.py`, `memory/ecphory.py` | Двухпутевая активация: векторный поиск + распространение по графу |
| Забывание | `memory/decay.py` | Кривые затухания, перевод в архив, потеря деталей |
| Консолидация | `memory/consolidation.py` | NREM-переигровка → REM-дистилляция → забывание |
| Фон | `memory/background.py` | Подшивка памяти по чуть-чуть, пока персонаж «в сети» |

### Как это работает

1. **Запись.** Реплика или внутреннее событие превращается в эпизод:
   текст, эмбеддинг, важность, неожиданность, эмоциональная окраска,
   источник (кто, какой чат) и провенанс.
2. **Индексация.** Эпизод получает временный «билетик» (labile tag)
   и, если прошёл порог, закрепляется. Слабые записи уходят в архив.
3. **Связывание.** Новый эпизод связывается с похожими —
   ассоциативный граф работает как CA3 в гиппокампе: подсказка
   вытягивает не только сам факт, но и соседние.
4. **Извлечение.** Запрос идёт двумя путями одновременно: по
   семантической похожести и по активации графа. ACT-R-ценность
   учитывает свежесть и частоту обращения — то, что вспоминали
   недавно, всплывает легче.
5. **Забывание.** Всё, что не подкрепляется, слабеет: сначала теряет
   детали, потом уходит из активного доступа. Это не баг, а механика —
   персонаж не должен помнить дословно всё.
6. **Консолидация во сне.** Во время сна эпизоды переигрываются
   (NREM), из них дистиллируются обобщения (REM), лишнее забывается.
   Утром память другая — не потому что «сбросили контекст», а потому
   что прошёл цикл.

### Что важно в дизайне

- **Провенанс у каждой записи.** У эпизода есть источник и чат.
  Смешивать воспоминания из разных чатов — ошибка, а не фича.
- **Битемпоральность.** У факта две оси времени: когда это было
  правдой и когда мы об этом узнали. Поэтому «он сказал X в марте»
  и «сейчас он говорит Y» не конфликтуют.
- **Память влияет на генерацию.** Извлечённое подмешивается в контекст
  вместе с эмоциональной окраской, а не просто как текст.

## Система аффекта

Аффект — не «настроение в промпте», а отдельный движок с состоянием,
которое живёт между сообщениями (`kuni/affect/`).

### Ядро: PAD + appraisal

Состояние описывается тремя осями:

- **valence** — насколько приятно (−1…1);
- **arousal** — насколько «колотит» (0…1);
- **dominance** — сколько контроля над ситуацией (0…1).

Плюс к этому — **appraisal**: не «что сказали», а *как персонаж это
оценил* по осям релевантности, соответствия цели и новизны.
Одна и та же фраза может дать разный результат в зависимости от
контекста и прошлого опыта.

### Нейрохимия как слой поверх

`affect/engine.py` держит медленные переменные (серотонин, норадреналин,
дофамин) и усталость. Они меняются медленно, гасят всплески и задают
фон: после долгого стресса реакция на новую грубость будет другой,
чем на пустом месте.

### Социальная боль

`affect/social.py` — отдельная модель отношений по каждому чату:

- потребности: принадлежность, уважение, контроль, смысл;
- **pain_index** — накопленная социальная боль;
- стадии: `none → reflexive → reflective → resignation`;
- счётчик повторов и статус «замолчала».

Это то, что не даёт персонажу реагировать на десятое оскорбление так
же, как на первое. Обида копится, доверие падает, вес отношений
(`w_rel`) меняется.

### Руминация

Если событие достаточно сильное, запускается «пережёвывание»
(`rumination_traces`): мысль возвращается, обрастает деталями и
постепенно тускнеет. Она влияет на сон и на то, что вспомнится
следующим.

### Модуляция речи

`affect/modulation.py` превращает состояние в **директиву стиля**:
при высоком arousal — короткие резкие фразы, при низком dominance
и обиде — паузы и многоточия, при истощении — минимум слов.
Промпт получает не «ты злая», а конкретное указание, как звучит
речь в этом состоянии.

### Защита от самоповреждения характера

`affect/safety.py` ограничивает крайности: состояние не может
уйти в бесконечную спираль, а сильные эмоции не превращаются
в сломанный текст.

## Сон

Сон — не таймер «не отвечать ночью», а цикл с фазами
(`affect/sleep.py`, `memory/consolidation.py`).

- **sleep_drive** растёт от усталости, когнитивной нагрузки и
  циркадного ритма.
- **Отсрочка сна.** Если идёт живой диалог или персонаж кому-то
  «должен» ответить (`CommitmentTracker`), сон откладывается —
  как у человека, который не может лечь, пока не дописал.
- **Фазы:** `awake → wind_down → nrem_sws → rem → wake_inertia`.
- **Влияние на поведение:** в `wind_down` речь короче и медленнее,
  в `wake_inertia` — спутанная, в `fragmented_wake` — раздражённая.
- **Влияние на память:** NREM переигрывает эпизоды, REM дистиллирует
  обобщения, лишнее забывается. Качество сна зависит от руминации и
  нагрузки — плохой сон даёт худшую консолидацию.
- **Ночная очередь.** Сообщения, пришедшие во сне, не теряются:
  они копятся и разбираются утром, с учётом того, что персонаж
  «только проснулся».

Отдельно есть `mental_state`: истощение, эрозия агентности, долг сна.
Это медленный слой — он меняется днями, а не сообщениями.

## Как это выглядит в чате

- **Дробление.** Длинный ответ уходит 1–3 репликами с паузами,
  а не полотном.
- **Печать.** Задержка зависит от длины и скорости набора.
- **Молчание.** Персонаж может прочитать и не ответить — это
  нормальное поведение, а не сбой.
- **Инициатива.** Отдельный слой (`proactivity/`) решает, хочется ли
  написать первой, кому и зачем. По умолчанию — «не хочется».
- **Реакции и стикеры** вместо слов, когда слов не нужно.
- **Границы.** На грубость есть ответ, на угрозу — отказ, на
  повторяющееся давление — тишина.

## Архитектура

```
kuni/
├── app.py            — оркестратор: приём сообщения → память → аффект → ответ
├── character/        — персонаж: промпты, эмоции, директива стиля
├── memory/           — эпизоды, граф, семантика, забывание, консолидация
├── affect/           — PAD, appraisal, социальная боль, руминация, сон
├── proactivity/      — импульсы, «написать первой», внутренний монолог
├── telegram/         — tdlib-клиент, «человеческое» поведение
├── llm/              — OpenAI-совместимый клиент (+ JSON-режим)
├── skills/           — инструменты персонажа (память, поиск, файлы)
├── harness/          — «руки»: чтение/правка кода с подтверждением
├── dashboard/        — веб-панель состояния
├── console/          — CLI-команды
└── infra/            — конфиг, шина событий, singleton, метрики
```

Подробнее: [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) и
[`docs/diagrams/`](docs/diagrams/) (слои, поток сообщения, память,
модули). Исследования, на которых построены модели:
[`docs/research/`](docs/research/) — аффект, холодность, память,
психика, сон, идентичность.

## Быстрый старт

```bash
python -m venv .venv
.venv\Scripts\activate              # Windows
pip install -e ".[telegram,dev]"

copy .env.example .env              # вписать ключи
python -m kuni init                 # создать config.toml
python -m kuni diagnose             # проверить окружение
python -m kuni login                # вход в Telegram (один раз)
python -m kuni run                  # запуск
```

Нужен свой `api_id` / `api_hash` с https://my.telegram.org и любой
OpenAI-совместимый LLM-эндпоинт (Ollama, vLLM, OpenRouter и т.п.).

Конфиг — `config.toml`, шаблон — `config.toml.example`.
Секреты — только через `.env`; в `config.toml` можно ссылаться
на них как `env:ИМЯ`.

## Известные ограничения

Проект в разработке, и это честный список:

- **Схема БД без миграций.** Таблицы создаются при старте; при
  изменении полей старые базы могут не читаться. Не для продакшена.
- **Консолидация во сне — эвристика**, а не полноценная модель
  переигровки: качество зависит от модели, которая её делает.
- **Долгая память деградирует** на очень больших объёмах: граф
  чистится, но поиск по нему пока линейный по глубине.
- **Несколько процессов не поддерживаются**: singleton-lock на
  один экземпляр.
- **tdlib-специфика.** Часть поведения (реакции, цитаты, кнопки)
  завязана на версию tdlib.
- **Локализация.** Промпты по умолчанию русские; английские
  требуют переписывания, а не перевода.
- **Нет веб-настройки всего.** Панель показывает состояние, но
  не заменяет `config.toml`.
